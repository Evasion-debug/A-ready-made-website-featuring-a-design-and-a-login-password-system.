# Подключение сайта к реальному серверу авторизации

Сейчас на сайте `site.html` вход и регистрация работают в «демо-режиме»:
пароли проверяются прямо в браузере, ничего не сохраняется на сервере,
и после перезагрузки страницы все аккаунты пропадают. Это удобно, чтобы
показать, как выглядит интерфейс, но для реального сайта, на который
будут заходить люди, нужен настоящий сервер. Ниже — как его подключить.

## 1. Что здесь лежит

Простой сервер на Node.js/Express с тремя вещами, которые нужны любой
системе логина:

- `POST /api/register` — создать аккаунт (пароль хэшируется через bcrypt,
  в открытом виде нигде не хранится)
- `POST /api/login` — проверить почту и пароль, выдать сессионный токен
- `GET /api/me` — узнать, кто сейчас авторизован (нужно, чтобы человек
  оставался в системе после обновления страницы)
- `POST /api/logout` — выйти

Токен сессии хранится в `httpOnly`-cookie — так его нельзя украсть через
JavaScript на странице, это заметно безопаснее, чем хранить токен в
`localStorage`.

Пользователи в этом примере хранятся в файле `users.json` — этого хватит,
чтобы всё запустить и проверить, но для реального сайта такой способ не
подходит (см. шаг 4).

## 2. Запуск локально

```bash
cd backend-example
npm install
cp .env.example .env
```

В `.env` впишите:
- `JWT_SECRET` — любая длинная случайная строка. Сгенерировать:
  ```bash
  node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
  ```
- `FRONTEND_ORIGIN` — адрес, с которого вы открываете `site.html`
  (например, `http://localhost:5500`, если открываете через Live Server)

Запуск:
```bash
npm start
```
Сервер поднимется на `http://localhost:4000`.

## 3. Подключение сайта к серверу

В `site.html` найдите блок `AUTH_CONFIG` (в самом начале скрипта, отвечающего
за авторизацию) и поменяйте два значения:

```js
const AUTH_CONFIG = {
  demoMode: false,                              // было true
  apiBase: 'http://localhost:4000/api'          // адрес вашего сервера
};
```

После этого формы входа и регистрации на сайте будут обращаться не к
встроенной демо-базе, а к настоящему серверу через `fetch`. Менять
остальной код не нужно — запросы уже написаны и ждут этого переключателя.

Дополнительно стоит добавить проверку сессии при загрузке страницы, чтобы
человек не разлогинивался при каждом обновлении — вызовите
`GET /api/me` в начале скрипта и, если он вернул пользователя, сразу
считайте его вошедшим.

## 4. Что поменять перед реальным запуском для всех пользователей

1. **База данных вместо файла.** `users.json` не выдержит одновременную
   запись от многих людей и потеряется при переустановке сервера.
   Возьмите одну из готовых баз:
   - [Supabase](https://supabase.com) или [Neon](https://neon.tech) —
     PostgreSQL с бесплатным тарифом, поднимается за пару минут
   - [MongoDB Atlas](https://www.mongodb.com/atlas) — если удобнее NoSQL
   Замените функции `readUsers`/`writeUsers` на запросы к базе через
   `pg`, `prisma` или `mongoose`.

2. **Хостинг сервера.** Локально сервер видите только вы. Чтобы он был
   доступен всем, разместите его на:
   - [Render](https://render.com) или [Railway](https://railway.app) —
     проще всего для маленького Node-сервера, есть бесплатный тариф
   - VPS (Timeweb, Selectel, DigitalOcean) — больше контроля, но нужно
     самому настраивать окружение

3. **HTTPS.** Логин и пароль обязательно должны идти по HTTPS, иначе их
   можно перехватить. Render/Railway выдают HTTPS-адрес автоматически;
   на своём VPS настройте его через Let's Encrypt (бесплатно).

4. **CORS и cookie.** `FRONTEND_ORIGIN` в `.env` должен быть настоящим
   адресом вашего сайта (например, `https://nothing-project.ru`), иначе
   браузер будет блокировать запросы. Также при хостинге на разных
   доменах (сайт и сервер) в `issueSessionCookie` понадобится
   `sameSite: 'none'` вместо `'lax'`.

5. **Домен для сервера.** Удобно завести поддомен вроде
   `api.ваш-сайт.ru` и направить его на сервер — тогда `apiBase` в
   `AUTH_CONFIG` станет `https://api.ваш-сайт.ru/api`.

## 5. Более простой путь — готовые сервисы авторизации

Если не хочется поддерживать свой сервер, можно подключить готовую
систему логина без написания бэкенда:

- **Supabase Auth** — почта/пароль, вход через Google и другие сервисы,
  бесплатный тариф, есть JS-библиотека для браузера
- **Firebase Authentication** — похожее решение от Google
- **Clerk** или **Auth0** — больше готовых компонентов интерфейса, но
  бесплатный тариф обычно ограничен числом пользователей

В этом случае формы на сайте останутся почти такими же, просто вместо
`fetch` к своему серверу вы вызываете методы SDK выбранного сервиса
(например, `supabase.auth.signInWithPassword({ email, password })`).

## Порядок действий, если коротко

1. Запустите сервер из этой папки локально и проверьте, что регистрация
   и вход работают через Postman/curl.
2. Переключите `AUTH_CONFIG.demoMode = false` на сайте и укажите адрес
   сервера — проверьте вход уже через сам сайт.
3. Замените `users.json` на настоящую базу данных.
4. Разместите сервер на хостинге, настройте HTTPS и домен.
5. Обновите `apiBase` на сайте на боевой адрес сервера.
